# 02 分支管理实践

本文档记录一次完整的分支管理流程：创建分支、在分支上提交、合并回主干、处理合并冲突。

## 一、为什么使用分支

分支（branch）本质上是一个指向某次提交的指针。开发新功能时在独立分支上进行，主干保持稳定；功能完成后再合并回主干，即使中途出错也只影响该分支。

## 二、创建与切换

```bash
git checkout -b feature-notes   # 创建并切换到 feature-notes 分支
git branch                      # 查看所有本地分支，带 * 的为当前分支
git checkout main               # 切回 main 分支
```

`git checkout -b` 相当于 `git branch <名字>` 加 `git checkout <名字>` 两条命令。

## 三、合并分支

```bash
git checkout main
git merge feature-notes
```

合并有两种常见结果：

- `Fast-forward`：目标分支在创建后没有被改动，Git 直接把指针前移，不产生新的合并提交
- `Merge made by the 'ort' strategy`：两个分支都有各自的提交，Git 生成一个新的合并提交

## 四、冲突的产生与解决

当两个分支修改了同一文件的同一区域时，Git 无法自动判断保留哪一份，就会在合并时报告冲突：

```
Auto-merging notes.md
CONFLICT (content): Merge conflict in notes.md
Automatic merge failed; fix conflicts and then commit the result.
```

打开冲突文件，会看到 `.git` 添加的冲突标记：

```
<<<<<<< HEAD
项目状态：文档完善中
=======
项目状态：功能开发中
>>>>>>> feature-notes
```

解决冲突的步骤：

1. 阅读两侧内容，决定保留哪一份或合并成新内容，并删除 `<<<<<<<`、`=======`、`>>>>>>>` 三类标记
2. `git add notes.md` 把解决后的文件标记为已解决
3. `git commit -m "解决 notes.md 的合并冲突"` 完成合并提交
4. `git log --oneline --graph` 确认历史呈现分叉后汇合的形状

## 五、合并后的分支处理

合并完成后，功能分支的提交已经进入主干，可以安全删除：

```bash
git branch -d feature-notes
```

如果分支尚未合并，Git 会拒绝删除并提示，需要确认确实不再需要时使用 `-D` 强制删除。

## 六、实践建议

- 一个分支只做一件事，分支名用 `feature/`、`fix/` 前缀区分类型
- 合并前先 `git pull`，减少与他人改动冲突的概率
- 遇到冲突不要慌，冲突标记只是文本，人工判断后删掉标记即可
